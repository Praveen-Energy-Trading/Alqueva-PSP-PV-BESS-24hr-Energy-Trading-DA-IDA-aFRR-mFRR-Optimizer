# Plan: an ML lifecycle dashboard for interviews

## Purpose

One section of the dashboard that tells the whole machine-learning story of this project in the order a real project runs, from raw
market data to a monitored model in production, so that in an interview you can click through it and show command of every stage.
Everything shown is real output of the work done (no mock-ups), and the limits are shown too: honesty is part of the message.

## What an interviewer should leave with

1. You can frame a forecasting problem correctly (what is forecast, what is known when, why a spread or a level).
2. You evaluate without leakage (rolling origin, locked test, point-in-time features) and test differences statistically.
3. You tune and compare models fairly (nested time-aware tuning, equal budgets, Holm-corrected tests).
4. You choose by a written rule, test once on locked data, and report what you found even when it is unflattering.
5. You run models like software: a registry, reproducibility, a promotion rule, monitoring, retraining, a safe live switch.

## Structure: nine pages in one "ML Lifecycle" group

The existing app is a Streamlit multipage app. The new pages form their own group in the navigation (Streamlit 1.51 supports
grouped navigation), above the current "ML Forecasting" page, which is replaced when the targets are switched (see Order).

| # | Page | What it shows (all from files that exist) | The point to make |
|---|---|---|---|
| 0 | **Overview: from data to decision** | The lifecycle as a clickable flow; a status badge per stage; headline numbers (6 targets with a champion, locked-year MAE per target, 607 tests, reproducibility) | The complete picture in one screen |
| 1 | **Data and quality** | Sources and what each provides; the raw zone (checksums, versions); regimes and structural breaks; quality score and gate; missing-day charts, including the rise of empty IDA1 auctions; 23-hour and 25-hour days | Data work comes first and is audited |
| 2 | **Market analysis** | Interactive price history by regime, seasonality, negative prices, spread against day-ahead, correlations, sample size per target | You looked at the data before modelling |
| 3 | **Problem formulation** | Per target: modelled quantity (level or spread), the information set on a timeline of gate times, the asinh transform, what a forecast is used for | You specify what is known when |
| 4 | **Features** | The catalogue (77 features) and an availability matrix per target; feature sets; stability selection; the point-in-time check explained | No leakage by construction |

Plus one **Interview mode** switch in the sidebar: a guided tour (next and previous buttons through pages 0 to 9), and a
**Model card** per target (intended use, data, performance, limits), the format hiring teams know.

## How it is built

- **A single data layer**, `dashboard/ml_data.py`, reads only committed files (`model_development/`, `config/`, `docs/`) and, when
  present, the registry database. Pages never compute; they read, cache (`st.cache_data`) and draw. This keeps the dashboard fast
  and means it shows the same numbers as the documents.
- **A demo data pack**, `model_development/data/`, generated by one tool from the run folders: the trials, daily loss per model,
  folds, and the locked-year forecasts in compact form (about 5 to 10 MB). Without it the interactive pages would need the
  large `runtime/` prediction files, which are not committed, so the demo would not work on a clean checkout or another laptop.
- **Monitoring is replayed, honestly labelled.** The locked year is a genuine out-of-sample year, so the monitoring page replays the
  rolling error against thresholds taken from the development window, marked "replay of the locked year", plus an optional
  "simulate a market change" button that shows the degradation flag firing (marked as a simulation).
- **Charts** in Plotly with the existing theme; the generated PNGs stay as the fallback and for the PDF.
- **Graceful degradation**: if the registry database is missing, the registry and monitoring page shows the committed snapshot
  and says so.

## Tests

- A unit test for each function of the data layer on small fixtures.
- Streamlit's `AppTest` opens every page headless and fails on any exception, empty chart or missing key element.
- A check that every number on the Overview equals the number in `model_development/RESULTS.md` and the locked-test files.
- A clean-checkout check: the pages render with the registry and `runtime/` absent.

## Risks

- Several pages show results that are still being produced (the locked tests of five targets, the champion registration). The data
  layer reads whatever exists and marks missing stages as "not yet run", so the pages work at every step.
- Showing the limits (artificial fill, limited evidence, the numerical failure) is deliberate. If you prefer a cleaner story, the
  strips can be collapsed by default, but I recommend leaving them visible: interviewers trust a project that reports its limits.
